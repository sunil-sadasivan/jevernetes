# Durable monitoring controller

`controller` continuously follows running Kubernetes containers using in-cluster service-account configuration. It requires an explicit namespace and an existing writable state directory. It has no mutation, exec, remediation or enforcement path. `files` and `k8s` keep their existing session behavior.

```sh
# Inside the prepared container; secrets are mounted by the operator.
jevernetes controller --namespace example --state /var/lib/jevernetes/state.db \
  --policy /etc/jevernetes/policy.json --sink webhook --verdict-ttl 300 \
  --selector app!=jevernetes
```

`--sink stdout` is the default and writes one notification JSON object per line. Redirect it to a private JSONL file for development. Controller status goes to stderr; `--output` writes the final bounded report. Before state creation/open or cluster access, report paths are checked against the database and its lock/journal/WAL sidecars, including normalized paths, symlinks (even dangling links) and Unix hard-link aliases. Unresolvable paths fail closed. The check repeats before the final report write. Keep both directories private and stable; validation is not a defense against an untrusted process concurrently replacing directory entries. `--json` and `--no-grouping` are rejected in controller mode. `--offline` disables Jev requests and yields review/abstention for uncached events; **it does not disable webhook delivery**. Existing valid durable judgments may still be reused offline. The fully offline test smoke below opens only a synthetic loopback webhook, without Kubernetes or provider configuration.

## Policy and reuse

A `--policy` JSON file (at most 16 KiB) overlays typed defaults; unknown fields are rejected. See `deploy/base/resources.json` for the complete default. All three finite choice confidences must be at least 0.85; importance must be `important`, category `security` or `fraud`, and severity `degraded`, `impact` or `outage`. The severity taxonomy is inherited from the operational classifier; tune it against labeled security/fraud data before relying on its routing. Confidence is a model score, not a calibrated probability of harm. Low confidence, incomplete/failed classification, unknown choices and truncation go to `review`; `abstention: "record"` records `abstain` without delivery. High-confidence out-of-scope or routine events are ignored by policy, never described as proof of safety.

Configurable fields: `categories` (up to nine known categories), `severities` (up to five known severities), `min_confidence` (0–1), `cooldown_seconds` (1–86,400), `recurrence_window_seconds` (1–604,800), `recurrence_count` (2–100,000), `max_escalation` (1–32), `abstention` (`review` or `record`). Defaults are 300-second cooldown, 900-second recurrence window, every fifth observation escalates, maximum level 8. This is an anchored window starting with the first observation after the previous window expires, not a sliding window. Both reviews and notifications participate. Escalation and a transition from the last enqueued `review` to `notify` bypass cooldown. The last enqueued decision class is durable, changes only with an outbox insert, and survives restart; suppressed observations cannot overwrite it. Level and notification sequence never decrease; expired windows reset the count only. Level exhaustion still permits cooldown reminders.

Cache identities use full SHA-256 over the provider identity, requested model, decision/redaction/truncation contract version, actual generated question instructions/taxonomy, every source field, full redacted text and truncation flag. No number, ID, stack frame or whitespace normalization is added. Timestamps are intentionally outside verdict identity; occurrences with identical evidence can reuse classification. Upstream redaction/JSON parsing still transforms input. Pin provider model revisions when available: a provider changing an alias cannot be detected by the local key. Bump `CONTRACT_VERSION` when non-prompt semantics change. `--verdict-ttl` is 1–604,800 seconds, default 300; reads honor both original expiry and the current shorter TTL. Reuse does not slide expiration. `--rescore` bypasses durable reads while preserving exact grouping within a microbatch. Failed, unknown, missing/invalid-confidence and truncated judgments never enter this cache. Successful `uncertain` judgments may be reused as review, never as routine.

Durable novelty fingerprints use exact source/text, timestamp and truncation state. Replayed evidence with the same decision signature is suppressed for seven days. Re-evaluating a changed policy, provider contract or decision can produce a new advisory notification, but does not increment recurrence for already-seen evidence. Changed confidence alone does not manufacture novelty. Keep the node clock synchronized: TTL, recurrence and durable retry times use UTC seconds. Backward clock jumps invalidate future-dated cache entries and can delay pending delivery until the clock catches up. Timestamp-less observations are treated as new because their occurrence identity cannot be proven. Legitimate identical messages at exactly the same timestamp can collapse; count-based escalation may therefore undercount. Conversely, process restarts, replay beyond retention, timestamp changes, or missing timestamps can overcount. This is deliberately **not exactly-once ingestion**. Durable stream cursors and multiplicity-aware occurrence IDs are deferred.

## Transactions and delivery

SQLite schema 2 uses a single serialized connection on blocking workers, 4 KiB pages, rollback journal and `synchronous=FULL`. A private sidecar lock prevents a second process from opening the same state path. A transaction persists eligible verdicts, novelty, incident state and notification intent together. An outbox insertion failure rolls everything back. There are no database locks across provider or sink requests. The worker reserves an attempt and a persistent rate slot before delivery. A crash before acknowledgment repeats the same notification ID after the 30-second lease; the receiver should deduplicate `Idempotency-Key`/`notification_id`. `incident_id` is stable across cooldown, recurrence and policy changes; each intended notification has a new monotonic sequence-derived ID.

Schema 1 upgrades transactionally to schema 2 at open. Migration recovers each incident’s last enqueued decision from its sequence-derived outbox ID, regardless of delivery status or timestamps. If that payload was pruned, the class remains unknown and the next Notify conservatively bypasses cooldown. A previously suppressed Notify can also recover on replay without incrementing recurrence; subsequent identical replays deduplicate. IDs, sequences, escalation levels and pending/dead rows are preserved. Invalid migration data rolls back the schema/version change; newer versions and nonempty unversioned databases are rejected. Back up a stopped store before upgrading; the old binary rejects schema 2. Notification payload schema remains 1.

One delivery worker reserves at most one attempt per UTC integer second, with no accumulated burst credit. Attempts across a clock-second boundary can be closer than one second. There are eight attempts, including interrupted attempts. Failed attempts back off by `min(300, 2^attempt + jitter)` seconds, with deterministic per-ID/attempt jitter 0–3 seconds. The last failed/expired attempt becomes `dead`. A canceled request remains pending until its lease expires. This is at-least-once delivery while retryable, followed by an explicit terminal dead letter; it is not a promise that an unreachable sink eventually accepts every alert. Pending and dead rows are never automatically deleted. Notifications do not block the ingestion or provider lanes.

Webhook URL and optional bearer token come from `JEV_WEBHOOK_URL`/`JEV_WEBHOOK_TOKEN`, or their `_FILE` counterparts. Environment values take precedence. Values/files are limited to 16 KiB, trimmed and rejected if empty; missing optional token configuration means no Authorization header. CLI arguments never accept these values. Production URLs must be HTTPS without userinfo or fragments; localhost HTTP is test-only. Auth headers are marked sensitive; URL/client objects have no Debug/Serialize implementation. TLS verification is enabled, redirects and environment proxies disabled, connect timeout 2 seconds, total HTTP timeout 5 seconds, outer delivery timeout 6 seconds. Payloads are capped at 128 KiB and responses at 8 KiB; response content and transport details never enter logs. Any non-2xx, oversized body or transport failure is retried within the attempt budget.

Payload schema 1 contains redacted evidence, a parsed evidence timestamp when available, typed judgment, exact applied policy, decision, count, level and IDs. Metadata allowlists type, namespace, pod, UID, container, kind, restart count and previous/current; strings accept only bounded identifier characters. Context labels, paths, annotations, labels and endpoint names are excluded. No raw source payload or model-generated action is delivered. The `Sink` trait is the extension point for Slack, PagerDuty, SIEM, Kafka and email; these adapters are not implemented.

## Exact bounds and failure behavior

| Resource | Limit/default |
| --- | --- |
| Input queue / batch / fill deadline | 1,024 events / 8 (maximum 64) / 350 ms |
| Active streams / retained report events | 64 / 2,000 |
| Line / event | 65,536 / 16,000 UTF-8 bytes |
| Provider lanes / attempts per batch | 1 / at most 3 |
| Per-process provider budget | 500 batches and estimated $0.25; rates are operator-supplied estimates |
| Verdict rows / timestamped novelty rows | 100,000 each |
| Incident identities / all outbox rows | 10,000 each |
| Database pages / size | 65,536 × 4 KiB = 256 MiB, plus transient rollback journal |
| Database busy timeout | 100 ms |
| Novelty / delivered outbox retention | 7 days |
| Pruning | At startup and every 60 seconds: at most 256 expired rows per table (verdicts, novelty, delivered outbox) |
| Incident tombstones / dead or pending outbox | Kept indefinitely within capacity; explicit operator maintenance required |
| Delivery | 1 in flight, 1 attempt/second, 8 attempts, 30-second crash lease |
| Health server | 1 connection at a time, 1 KiB request read, 1-second connection deadline |

The database reuses freed pages; pruning does not shrink the file. Incident tombstones preserve lifetime IDs/sequences/levels and can eventually fill the incident table. A full table/disk, corruption, unsupported schema, failed transaction or unavailable store is fatal and observable: readiness is latched false, counters/gaps increase, collection stops, and the process exits 1. The current event becomes unknown if persistence fails. No best-effort in-memory substitute silently declares it routine. Initial open failures are reported on stderr before starting collection. Operators must provision/monitor storage and investigate capacity before restarting; repeated restarts are not repair.

Log ingestion before the SQLite transaction remains volatile. A crash can lose queued/uncommitted evidence; replay is constrained by Kubernetes log retention and the `--since` (1h) / `--tail` (500) window. Failed notifications survive restart. Provider usage/cost counters and batch limits are per process, **not durable financial limits**; repeated restarts reset those limits and can spend again. Set external account quotas for a real spending ceiling. On new work after budget exhaustion the controller cancels collection; queued unrequested evidence becomes unknown/review. Report/metrics always retain partial-coverage semantics. Notification failure alone does not stop collection or make readiness false; growing pending/dead counts require operator attention.

SIGINT/SIGTERM cancels collection/provider requests, flushes/drains the bounded queue, commits policy/outbox for drained evidence, then cancels delivery and health tasks. Outbox intent survives cancellation. SQLite FULL-sync latency and a slow local disk can extend shutdown; the manifest allows 60 seconds, but no latency claim is made without testing the target volume.

The development stdout sink owns one dedicated OS writer thread and at most one outstanding bounded write/flush, separate from Tokio’s blocking pool. A timeout or cancellation cannot release that write’s slot; retries fail busy until it completes, consuming the normal durable retry/dead-letter budget without queuing more writes. A permanently blocked pipe can stop this sink from making progress, but cannot starve SQLite ingestion or delay controller/runtime shutdown. Shutdown does not join the stuck thread. A late write may still appear after timeout/dead-letter, so stdout has the same duplicate/ambiguous-acknowledgment limitation as other transports. Keep it drained and monitor dead letters; it is a development sink. No shutdown network flush is required for durability.

`GET /livez` reports the serving process; `GET /readyz` reflects required local state, independently of provider/webhook reachability. Periodic store work detects idle-state failure within roughly 60 seconds. `GET /metrics` emits Prometheus text, including `verdict_hits`, `verdict_misses`, `verdict_expirations`, `store_failures`, `state_pruned`, `novelty_duplicates`, policy decisions, outbox pending/dead, delivery attempts/failures, queue depth/high-water/dropped, coverage gaps, provider batches/attempts/tokens/unmetered requests and estimated cost. All names have the `jevernetes_` prefix. Counters reset on restart; outbox gauges repopulate from disk. `jevernetes_coverage_complete` is always 0. Zero alerts or low cost never implies absence of risk.

Alert on state failure/unready, any dead letters, sustained pending backlog, unmetered provider requests, drops, unfollowed observations and coverage gaps. The health listener defaults to `0.0.0.0:9090`, has no authentication and exposes no event payloads; restrict network access using site policy. No per-source metric labels introduce unbounded cardinality.

## Deployment and maintenance

`deploy/base` is a Kustomize base with namespace-scoped read-only pod/log RBAC, one replica with Recreate strategy, a 1 GiB RWO PVC, Secret references, non-root UID/GID 65532, dropped capabilities, RuntimeDefault seccomp, read-only root filesystem and resource requests/limits. The example only observes its namespace; adapt namespace and RBAC together for your workload. Never bind this identity to Secret-read or mutation permissions. No Secret values are provided. Provision `controller-jev` key `api-key` and `controller-webhook` key `url` through your approved secret manager. Optional `controller-webhook-auth` key `token` is projected; enable `JEV_WEBHOOK_TOKEN_FILE=/var/run/jevernetes-secrets/webhook-token` only when that Secret exists. Secrets are read once at startup; restart to rotate them. The base excludes `app=jevernetes` to avoid reviewing its own logs. Preserve an equivalent exclusion when changing labels/selectors to prevent notification feedback loops.

The Dockerfile requires `RUST_IMAGE` and `RUNTIME_IMAGE` build arguments, selected and digest-pinned by the operator (Rust 1.94+, compatible Debian slim runtime). Replace the deliberately non-deployable `example.invalid/jevernetes:REPLACE_ME` image. The build installs CA certificates and copies only the release executable. No actual registry tag, credential or private endpoint is selected. Local validation:

```sh
python3 tools/check_controller_artifacts.py
kubectl kustomize deploy/base > /tmp/controller-rendered.yaml
cargo test --all-features controller::tests::offline_controller_smoke_and_shutdown
```

These commands do not deploy. Image build, target-cluster schema/admission validation, filesystem durability and resource sizing still require an authorized environment. Use a filesystem supporting local advisory locks and SQLite durability; no NFS/shared SQLite volume. RWO alone is not a multiwriter protocol. Scale by exclusive source shards with independent volumes, or migrate incident/outbox ownership into a transactional server database with leases before adding replicas. Do not copy live database files; use SQLite backup support or stop the process before backing up the database and sidecars. Storage encryption, access controls and secure deletion are operator responsibilities.

For dead-letter visibility, inspect a **private, stopped copy** with SQLite: `SELECT id,incident,attempts,updated FROM outbox WHERE status='dead';`. After fixing the receiver, an operator can deliberately requeue selected IDs with `status='pending', attempts=0, due=0`; preserving IDs makes retries deduplicable. Back up first, never modify a running store, and never bulk-delete pending/dead rows to clear capacity. No built-in requeue/acknowledgment, incident archive/migration or outcome-feedback CLI is included yet. Deleting the database resets novelty and incident identity history and is not ordinary pruning.

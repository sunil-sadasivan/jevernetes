# Initial release security review

Reviewed on 2026-09-20 for version 0.1.0. This is a maintainer review of the source, regression tests and release artifacts, not an independent penetration test or a guarantee that vulnerabilities do not exist.

## Outcome and scope

No unresolved high- or critical-severity issue was identified in the reviewed scope. The review covered browser rendering and clipboard export, local HTTP access controls, subprocess argument handling, Kubernetes context identity, redaction, file/resource limits, provider authentication and redirects, local report/rule persistence, and package contents. The supported deployment remains a trusted user's loopback-only local tool.

The release was prepared in a clean checkout containing only source, documentation and synthetic fixtures. Local runtime reports, review rules, kubeconfigs, environment files and generated bytecode were never added to its Git history. A separate identifier scan checked for private project names, personal paths, cluster endpoints and real-log identifying data. Git commits use the maintainer's GitHub no-reply address.

## Checks and findings

- 74 Python tests pass, including HTTP Host/Origin/token checks, path restrictions, redaction, bounded decompression, invalid model answers, context-instance validation, and reversible review overrides.
- JavaScript checks cover source/context filtering and investigation-prompt generation. Selected evidence is represented as JSON with explicit untrusted-input instructions; copying is user-initiated and makes no AI requests.
- TruffleHog 3.97.1 scanned the clean tree with credential verification and update checks disabled. Its one finding was the deliberately synthetic PostgreSQL URL in `tests/test_analyzer.py`, used to test password redaction. No real credentials were found. No candidate credentials were sent to verification services. The fixture now has a narrowly scoped inline ignore, verified by a clean rerun; no file or detector is excluded. CI pins TruffleHog 3.97.5.
- Bandit 1.9.4 reported zero high- or medium-severity findings and five low-severity findings. These were reviewed: retry jitter uses non-cryptographic randomness, and Kubernetes uses the subprocess module and a PATH-resolved `kubectl`. Commands use argument lists without a shell; PATH and kubeconfig plugins are explicitly trusted local configuration. Random jitter is not used for tokens or authentication; security tokens use `secrets`.
- Release-content checks inspect tracked files, wheel and source archive for runtime data, configuration, private key files, bytecode, credential-shaped strings and personal filesystem paths. GitHub Actions use pinned commits and read-only repository permissions.

## Hardening during review

- Added a 32 MiB default decompressed input cap, including blank and oversized lines, to bound compressed/hostile file processing.
- Extended redaction for escaped quoted values, access/private-key fields, and PEM private-key blocks split across log lines.
- Rejected option-like Kubernetes input after whitespace normalization.
- Added regression coverage for those cases and for selected-event prompt size limits and evidence preservation.

## Remaining limitations

The loopback API is not an authentication boundary against other local users/processes. The HTTP server is intended for local use, not hostile multi-user hosting. Logs and copied prompts can contain personal data or uncommon secrets despite redaction. Jev classifications can be wrong, expected-event patterns can be overly broad, and cost thresholds are estimates rather than billing caps. Kubernetes log rotation can make context unavailable. No independent audit or browser visual QA is claimed. See SECURITY.md for operational boundaries and private reporting.

## Ongoing automation

Dependabot, TruffleHog, Bandit, pip-audit and CodeQL are configured for ongoing checks. See CONTRIBUTING.md for triggers, permissions, thresholds and the one synthetic fixture suppression.

# Deployment templates

`base/resources.json` is a namespaced read-only controller example with pod get/list/watch and pod-log get permissions. Replace the example image and configure namespace, selection, provider secrets and webhook endpoint through your own delivery process. These files are not applied by tests or release scripts.

Build the multi-stage Dockerfile with operator-approved digest-pinned `GO_IMAGE` (Go 1.25+) and Debian-compatible `RUNTIME_IMAGE`. Runtime user/group is 65532; provision `/var/lib/jevernetes` privately and use local persistent storage. The binary includes dashboard assets and requires no interpreter. The checked-in security context uses a read-only root filesystem, no privilege escalation and dropped capabilities.

Health/metrics use port 9090. Inspection is enabled on loopback 9091 and is deliberately absent from the Service. Inspecting operators separately need pod get/list and pods/portforward create; do not grant those additional permissions to the collector merely for inspection.

`reviewed-rules.patch.json` is an optional overlay for an independently reviewed artifact. Mount schema-1/artifact-version-2 JSON as described in [template learning](../docs/provider-template-learning.md). The Go loader rejects unsupported logger-clock prefixes. No example rule or policy establishes production safety.

The process fails closed on invalid policy, state schema, price, selection and rule configuration. State schema 3 changes notification payloads to metadata-only schema 2; coordinate consumer upgrades and backups before deployment. See [controller operations](../docs/controller.md).

## Private state volume and legacy upgrades

Keep the single replica and `Recreate` strategy. The pod retains `fsGroup: 65532` so an unprivileged process can initially access the PVC root. A direct mount of that group-accessible root would violate the state opener's current-user-owned private directory requirement. The `prepare-state` init container runs as UID/GID 65532 after volume ownership processing, creates `private` with mode 0700, and restores that mode on subsequent starts (fsGroup can widen existing modes again). It also restores known state files to 0600. The main container mounts `subPath: private` directly at `/var/lib/jevernetes`; its exact state path remains `/var/lib/jevernetes/state.db`. Image ancestors must retain protected root/current-user ownership and non-writable permissions. The state opener retains its restrictive directory contract and independently validates any existing SHM before SQLite initialization; direct `controller --state` use does not depend on preparation.

Both containers use the same image. Replace **both** image references with the same approved immutable digest, preferably through Kustomize's `images` transformer. The init container explicitly runs `/usr/local/bin/jevernetes prepare-state-volume /state-volume`, overriding the image entrypoint with the same executable; it requires no shell or additional image. It mounts the PVC root, with no provider secret mounts/environment, and retains non-root execution, RuntimeDefault seccomp, a read-only root filesystem, no privilege escalation and all capabilities dropped.

Before upgrading, stop all volume users and preserve a volume snapshot/backup including recovery files. Use a dedicated local filesystem volume with working Unix locks, rename and fsync; network filesystems are unsupported. `Recreate` orders this Deployment's normal upgrade, but ReadWriteOnce and advisory locks do not fence unrelated pods, manual processes or a force-deleted old writer. Do not share this volume or UID with other writers. Existing state files and `private`, if present, must already belong to UID 65532; the helper never takes ownership of foreign files. The volume root must be root/UID-65532 owned, GID 65532 and not world-writable.

When `private` is absent or empty, preparation migrates exactly `state.db`, `state.db.lock`, `state.db-journal`, `state.db-wal` and `state.db-shm` from the old root (only present artifacts are moved; a writer lock is created if needed). A database must accompany any legacy sidecars. It checks regular-file type, ownership, single links and no symlinks, takes preparation/writer locks, syncs files, moves recovery artifacts before the database into `.private-migration`, syncs both directories after each move, then publishes the complete directory as `private` with one rename and syncs the root. It never opens SQLite or changes file contents during preparation. SQLite performs any recovery when the controller opens the migrated database.

A populated `private` plus any legacy artifacts, orphan sidecars, unknown `state.db*` names, unexpected entries inside `private`, unsafe file types/owners/links, held locks, or an existing `.private-migration` fail closed. Unrelated root metadata such as `lost+found` is left in place. A healthy existing `private` is normalized and reused. No conflicting state is overwritten or deleted.

Preparation preserves real WAL/SHM bytes along with the database; it does not open SQLite or perform recovery. On the controller's first open, SQLite rebuilds shared memory, recovers committed WAL rows and returns to DELETE journaling. Offline tests verify this with a crashed pinned-driver WAL, including missing SHM, all 2,000 committed rows and `integrity_check`. Ordinary DELETE databases do not acquire an unused SHM from the startup checks. The private directory excludes other OS identities, but root or a concurrent process with the controller's identity can still replace names between validation and SQLite's path-based opens; keep the volume exclusive to the controller. See the [state opening contract](../docs/controller.md) for the precise race limitation.

If preparation fails, keep the Deployment stopped and preserve **the entire volume**, including the root, `private`, `.private-migration`, database, journals, WAL/SHM and locks. An interrupted migration deliberately requires operator recovery; retries never infer how split artifacts belong together. On an isolated backup copy, establish one coherent database/recovery-file generation and verify it with SQLite. Restore that complete generation to either the legacy root with an absent/empty `private`, or to `private` with no legacy artifacts. Resolve staging/conflicting copies only after a verified backup and explicit operator decision; never discard recovery files simply to make initialization pass. Repair ownership as a separate operator action if necessary, then rerun preparation as UID/GID 65532 before restarting. This binary command is offline and does not read provider or Kubernetes configuration.
